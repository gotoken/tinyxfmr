# 教材開発ガイド

## 目的

この文書は、tinyxfmr の教材本文、GUI、実装例を追加・レビューするときの共通基準を定めます。

表示レイアウトやサイトナビゲーションの詳細設計は別途行います。ここでは教材としての一貫性と実装上の原則を扱います。

## 1. 開発の優先順位

優先順位は次の通りです。

1. 説明が数学的・アルゴリズム的に正しいこと
2. 前の内容から新しい内容が必要になる理由が自然であること
3. GUIで本文の説明を検証できること
4. コードが説明したアルゴリズムと対応していること
5. 自習で前から順に読めること
6. 実行が十分速いこと
7. 表示上の洗練

性能や抽象化のために1〜4を犠牲にしません。

## 2. 各セクションの設計テンプレート

すべてのセクションが全項目を必要とするわけではありませんが、原則として以下を検討します。

### 問い

このセクションで読者が考える具体的な問いを1つに絞ります。

例:

- 「直前の文字が違うと予測を変えた方がよいのでは？」
- 「確率を直接自由に変更するのはなぜ不便なのか？」
- 「遠い過去のどこを見るかをモデル自身に決めさせられないか？」

### 前提

この時点までに読者が知っていることだけを列挙します。未導入の用語を説明に使わないよう確認します。

### 実験

GUIで操作する内容と、観察してほしい現象を定義します。

### 発見

実験から何が不足しているか、どんな性質が欲しいかを平易な日本語でまとめます。

### 数式

必要になった操作を一般化します。数式は目的、各記号、利点を説明してから使用します。

### 名称

操作や対象を理解したあとで一般的な名称を付けます。

### コード

式と処理の対応を追います。コード片だけでなく、処理順序を文章で説明します。

### まとめ

「何ができるようになったか」と「まだ何ができないか」を記載し、次のセクション・次回への接続を作ります。

## 3. GUIの要件

GUIは本文と同じアルゴリズムを操作するものとし、説明専用の作り物の値を表示しません。簡略モデルを使う場合は、その簡略化を明記します。

各GUIについて検討する項目:

- 初期状態が意味を持つこと
- 実行できること
- 元の状態にリセットできること
- 同じseedで再現できること（乱数を使う場合）
- 変更可能な値と固定値が区別できること
- 本文で言及する中間値を確認できること
- 正解だけでなく失敗例も確認できること
- 異常な入力を与えても教材全体が壊れないこと

学習GUIでは可能な範囲で以下を見せます。

- step
- loss
- 現在の予測
- parameterまたは代表値の変化
- attentionなど、その回で扱う中間状態

## 4. コードの要件

教材コードは「短さ」より「対応の明瞭さ」を重視します。

### 推奨

- 素直なループと配列操作
- 教材の数式と対応する変数名
- 小さく分割した関数
- 中間値を返す、または観察可能にする構造
- 決定的なテストデータ
- GUIと計算ロジックの分離

### 避ける

- 説明前の高度な言語機能への依存
- 何段階もの暗黙変換
- 数式と対応しない過度な抽象化
- 可読性を下げる早すぎる最適化
- 教材用ロジックと描画コードの密結合

高速化が必要な場合は、まず教育用の参照実装を残したうえで高速版を追加することを検討します。

## 5. 数式とコードの対応

主要アルゴリズムについて、最終的には次の3つを相互に行き来できるようにします。

1. 日本語による操作説明
2. 数式
3. 実装

たとえばsoftmaxなら:

- 日本語: scoreをexpで正の重みに戻し、合計で割って確率にする
- 数式: `p_i = exp(s_i) / Σ_j exp(s_j)`
- コード: 最大値を引く数値安定化を含む具体的なループ

実装で数値安定化など教材本文にない処理を追加する場合は、「数学的には同じだが計算機上で安全にするための処理」として明示します。

## 6. 数学コラムの要件

数学コラムは補足雑学ではなく、本文で使う数学を正しく理解するための前提教材です。

コラムは原則として以下を含みます。

- 何のために必要か
- 定義
- 最小限の計算例
- 本文中のどの式に使うか
- 誤解しやすい点（必要な場合）

高校範囲を超えるかどうかよりも、必要な内容を正確に説明できているかを優先します。

## 7. 用語導入のレビュー

新しい技術用語を追加するPRでは、次を確認します。

- その用語が初めて現れる場所は特定できるか
- その直前までに必要性が説明されているか
- 用語なしで操作を説明できているか
- 比喩だけで定義していないか
- 数式またはアルゴリズムとの対応が示されているか

特に以下は天下りになりやすいため注意します。

- embedding
- logits / score
- softmax
- loss / cross entropy
- gradient
- query / key / value
- attention
- head
- residual connection
- layer normalization
- positional encoding / embedding

## 8. 教材全体の連続性

各回・各セクションは、単独では正しくても前後関係が不自然なら修正対象です。

レビュー時には「この概念を、読者がこの時点で欲しいと思うか」を確認します。

後の説明のためだけに早い段階で概念を導入することは避け、必要になった時点で導入します。

## 9. 最終課題から逆算した要件

最終課題として、小さなTransformerによる閉じたしりとりを想定します。

最終課題では少なくとも以下を観察可能にします。

- 語末から次の語頭をつなぐこと
- 候補語の選択
- 過去に使った語を参照すること
- 再利用を禁止したときの成功率と失敗
- attention map
- 学習前後の予測変化
- model sizeによる能力差（発展）

最終課題にしか現れない仕組みを極力なくし、それまでの各回で必要な部品を一つずつ導入します。

## 10. 静的配信としての技術方針

現時点では静的コンテンツとして配信することを前提とします。

- 教材閲覧にサーバーサイド処理を必須としない
- 基本的な実験はブラウザ内で完結させる
- 学習データやモデル定義は教材と一緒に配布可能なサイズに保つ
- 外部APIがないと核心部分を試せない構成にしない
- オフライン利用可能性は将来検討できるよう、計算ロジックを局所化する

フレームワーク、ビルド方式、ホスティング、URL設計は別途決定します。

## 11. テスト方針

教材では表示の正しさだけでなく、説明している数学と実装が一致していることをテストします。

例:

- 頻度から得た確率が期待値と一致する
- softmaxの総和が1になる
- 全logitに同じ定数を足してもsoftmaxが変わらない
- causal maskにより未来位置を参照しない
- 手計算可能な小例でattention出力が一致する
- parameter更新前後で期待した方向にlossが変化する
- 固定seedで教材の主要デモが再現する
- しりとり評価指標が既知の列に対して正しい

## 12. コンテンツレビューのチェックリスト

教材内容を追加・変更するときは最低限以下を確認します。

- [ ] このセクションの問いが1文で言える
- [ ] 新概念の必要性が直前の問題から説明されている
- [ ] 未導入の用語を前提にしていない
- [ ] 数式を使う目的と利点が書かれている
- [ ] 必要な数学コラムへの導線がある
- [ ] GUIで主要な説明を確認できる
- [ ] GUIの値と本文・コードが同じ計算に基づいている
- [ ] コードとアルゴリズムの対応説明がある
- [ ] その回の到達点をまとめで確認できる
- [ ] 次に残る問題が明確である
- [ ] 比喩を定義の代わりにしていない
- [ ] ブラックボックス化している計算が新たに増えていない

## 13. 初期開発順序

教材全体を同時に作らず、以下の順で進めます。

1. 教材設計原則とカリキュラムをレビューして固定する
2. 第1〜3回を試作し、ストーリーの粒度とGUIの基本形を検証する
3. softmaxまでの導入が自然に読めるかを重点レビューする
4. 第4〜7回でEmbeddingからSelf-Attentionまでを接続する
5. 第8〜9回でTransformer blockと学習を接続する
6. 第10回のしりとりを統合する
7. 全体を通読し、後から追加された前提・天下りの概念を除去する
8. レイアウト、ナビゲーション、公開方法を別途設計する

最初の実装では網羅性より、最初の数回が本当にボトムアップで理解できるかを優先します。
